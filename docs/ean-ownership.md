# Принадлежность EAN товару

Правило: непустой EAN из любой колонки `Ean` может принадлежать только одному
`kid_id`, включая архив. Внутри одного KID повторение между площадками,
аккаунтами, основными EAN и резервами разрешено. Пробелы по краям не позволяют
обойти проверку. Пустые значения, `0000000000000`, `B_WARE` и `B-WARE` не являются
продуктовыми идентификаторами. Проверяется полная строка идентификатора:
артикул с суффиксом `_SOFORT` не преобразуется в числовой EAN автоматически.

## Реализация

- `Ean.save()` проверяет новые и изменённые значения. Это общий путь обычных
  create/update, импорта и подтверждения marketplace mapping.
- На PostgreSQL используются transaction-scoped advisory locks по EAN в
  стабильном порядке. Проверка и запись входят в одну транзакцию.
- API возвращает HTTP 409 `ean_owned_by_another_kid` с EAN и KID владельца.
  Частичные изменения в composite update откатываются вместе с конфликтом.
- Автовыдача из пула исключает значения из всех колонок `Ean`, даже если в пуле
  ошибочно указан статус `free`. Старый конфликтующий резерв не переиспользуется
  и не заменяется новым EAN молча. Резерв того же KID остаётся идемпотентным.
- Существующие конфликты не исправляются автоматически. Неизменённое старое
  значение можно сохранить или очистить; новая конфликтующая привязка запрещена.

## Границы и выкладка

Если номер KID соответствует нескольким записям, резервирование EAN,
отметка резерва как использованного и подтверждение привязки требуют точный
`kid_id`. Номер и ID должны относиться к одной записи. Выбирайте товар по
месту, фото и EAN в Sofort list и запускайте Create Product из нужной строки.
Дубликаты номера не объединяются. Для передачи `kid_id` в пул нужны
обновлённые database-service и orchestrator.

Проверка относится к локальному владению EAN, а не к достоверности карточки
провайдера. Подтверждение mapping выполняется после marketplace-запроса:
отказ записи не отменяет уже выполненный внешний запрос. Исторические данные
не исправляются и товары не перепубликуются.

Текущие production-пути записи используют `save()`/`create()`/`get_or_create()`.
Прямой SQL, `QuerySet.update()` и bulk-операции обходят model save и не должны
использоваться для новых привязок EAN. Это прикладная защита, не SQL constraint;
при появлении других писателей потребуется отдельный реестр владения с
ограничением уникальности и согласованной миграцией существующих конфликтов.

Нет новых колонок, migrations, env-переменных или frontend-изменений.
Сначала обновляется database-service, затем orchestrator; откат — предыдущие
образы. Между обновлениями запросы со спорным KID без ID отклоняются.
На время rolling deploy старый
код ещё может писать без новой проверки. Перед выкладкой нужен PostgreSQL-тест
`database.tests_ean_ownership.EanOwnershipConcurrencyTests`; SQLite его пропускает.

Изменения локальные. Production, старые EAN и marketplace-карточки не изменены.
